# Projeto final do módulo

Chegou a hora de transformar toda a sua base em um projeto real. Até aqui, você viu lógica, estruturas de dados, módulos, arquivos, testes, APIs, SQLite, classes e organização do código. Agora, em vez de resolver exercícios isolados, você vai escolher uma direção e entregar um sistema completo de terminal com regras de negócio, persistência, documentação e validação.

O grande cuidado aqui não é “fazer tudo de uma vez”. O que vale é decidir um escopo realista, dividir em partes pequenas, testar cada parte e manter a entrega organizada. Se o projeto for bem definido e bem estruturado, ele funciona como um portfólio: você pode apresentar o resultado para alguém e falar com segurança como ele foi concebido.

## 1. Como escolher a opção certa

A escolha do projeto final deve ser feita com base em três critérios: interesse, complexidade e tempo. Você não precisa escolher o tema mais difícil; precisa escolher o tema que você consegue desenvolver com clareza e entregar corretamente.

Se você gosta de analisar dados, finanças e relatórios, a opção de finanças pessoais é uma boa escolha. Se você gosta de logística e regras de negócio, estoque e vendas pode ser melhor. Se você tem mais afinidade com organização, produtividade e filtros, tarefas com prioridades é o caminho mais natural.

A ideia central é esta: o sistema precisa resolver um problema real de uso e ter estrutura fácil de evoluir. Não importa se o projeto é “simples” do ponto de vista visual; o que importa é que a lógica funcione, que o código seja legível e que a entrega tenha testes e documentação.

## 2. Os 10 requisitos obrigatórios

Ao entregar o projeto final, você deve cumprir os 10 requisitos a seguir. Eles não são “extras”. Eles representam a base de um sistema de qualidade profissional.

<ol>
  <li>Menu interativo em loop, com opção de sair.</li>
  <li>Uso de <Glossario termo="classes" definition="Estruturas que agrupam dados e comportamentos em um conceito do domínio, como Produto ou Tarefa." /> para as entidades principais.</li>
  <li>Funções bem separadas e com <Glossario termo="docstring" definition="Texto explicativo dentro da função que descreve o que ela faz e como deve ser usada." />.</li>
  <li>Persistência em <Glossario termo="SQLite" definition="Banco de dados leve em arquivo local, muito usado em projetos Python simples e confiáveis." /> ou em JSON.</li>
  <li>Tratamento de erros em toda entrada do usuário e em todas as operações de arquivo ou banco.</li>
  <li>Pelo menos um relatório, em texto formatado ou em CSV.</li>
  <li>Testes com `pytest` para as regras de negócio principais; mínimo 10 testes.</li>
  <li>Código organizado em módulos, com pelo menos 4 arquivos.</li>
  <li>README com instalação, uso e exemplo.</li>
  <li>Repositório Git com histórico de commits coerente.</li>
</ol>

Os requisitos mais importantes aqui são os que aparecem em qualquer projeto real: regras de negócio, validação, organização, persistência e testes. O aluno que entrega um projeto sem testes ou sem README geralmente não consegue explicar bem como a solução funciona. Por isso, o projeto final não é só “um app em Python”; ele é uma demonstração de capacidade de engenharia.

## 3. Estrutura de pastas recomendada

Uma boa estrutura ajuda muito porque separa responsabilidades e evita misturar “menu”, “banco”, “regras de negócio” e “relatórios” em um único arquivo. A recomendação abaixo é simples e funciona bem para qualquer opção do projeto final:

```text
projeto_final/
├── app/
│   ├── __init__.py
│   ├── banco.py
│   ├── modelos.py
│   ├── menu.py
│   ├── regras.py
│   ├── relatorios.py
│   └── validacoes.py
├── tests/
│   ├── test_modelos.py
│   ├── test_regras.py
│   └── test_relatorios.py
├── main.py
├── README.md
├── .gitignore
├── requirements.txt
└── dados.db
```

O nome dos arquivos é menos importante do que a divisão de responsabilidade. O `banco.py` cuida do SQLite; o `modelos.py` guarda classes e dados; o `regras.py` concentra validações e lógica de negócio; o `menu.py` cuida da interação com o usuário. Assim, você consegue testar cada parte separadamente.

<CodeBlock title="exemplo_estrutura.py" code={`# Estrutura sem código de sistema, apenas para pensar na separação
# main.py -> inicia o programa
# app/modelos.py -> classes e entidades
# app/banco.py -> conexão e SQL
# app/regras.py -> regras de negócio e validações
# app/relatorios.py -> resumos e CSV
# tests/ -> testes automatizados`} />

## 6. Opções do projeto final

O módulo oferece três caminhos principais. Cada um deles é um sistema completo, com regras de negócio distintas e estruturas possíveis de serem desenvolvidas em terminal.

### A. Gerenciador de finanças pessoais
- Receitas, despesas, categorias e saldo.
- Relatório mensal e metas de economia.
- Ideal para quem gosta de lógica financeira e análise.

### B. Sistema de estoque e vendas
- Produtos, entradas, saídas, estoque mínimo e lucro.
- Ideal para quem gosta de regras de negócio e controle operacional.

### C. Gerenciador de tarefas com prioridades
- Projetos, tarefas, prazos e filtros por urgência.
- Ideal para quem gosta de organização e produtividade.

Essas três opções cumprem o mesmo objetivo: entregar um sistema completo, com regras, persistência e documentação. O que muda é a área de domínio.

## 7. Padrão de entrega recomendado

Para aumentar a chance de sucesso, siga este roteiro simples:

1. Escolha a opção e escreva a ideia em 3 ou 4 frases.
2. Defina as entidades principais e as classes que elas terão.
3. Crie o banco ou o arquivo de dados e decida onde cada coisa será salva.
4. Monte o menu principal e teste uma opção por vez.
5. Crie testes para as regras mais importantes.
6. Escreva o README e registre os commits no Git.
7. Revise a organização e limpe o código antes da entrega.

# 5. Validar regras com testes
# 6. Documentar no README
# 7. Registrar commits` } />

## No mercado de trabalho

Projetos como esses aparecem em pequenos sistemas internos, ferramentas de gestão, dashboards de operação e portfólios de desenvolvimento. O que eles destacam não é apenas “o código funciona”. O que faz diferença é que ele está organizado, é testável, entende regras de negócio reais e possui documentação.

Em empresas, a pessoa que consegue entregar um sistema funcional com testes, estrutura e histórico de commits é vista como alguém que pensa além do código. Ela entende que software também é processo: decidir escopo, dividir tarefas, validar risco e manter a entrega consistente.
