# Depuração: encontrar a causa, não só o sintoma

Quando o programa quebra, a primeira reação natural é frustração. Mas um traceback não é um castigo; ele é um mapa. Cada linha mostra um trecho do caminho que o Python percorreu antes de encontrar o erro. Ler isso com calma é muitas vezes a diferença entre corrigir em 10 minutos e perder uma hora tentando adivinhar.

<Callout type="importante" title="O que você vai aprender">
  - Como interpretar um traceback e identificar a linha que causou o problema.
  - Quando usar `print`, `breakpoint()` e o debugger do VS Code.
  - Como seguir o método científico: hipótese → teste → correção.
  - Como evitar “caçar o bug” sem observar o estado real do programa.
</Callout>

## Depuração começa antes do erro

O método científico funciona bem aqui. Você observa o comportamento, cria uma hipótese sobre a causa, executa um teste pequeno e confirma ou descarta a ideia. Em vez de “isso parece estar errado”, você pergunta: “qual é o valor de x nesse ponto?”

Esse processo é muito útil em funções pequenas e em programas maiores. Você não precisa começar pela solução completa, mas sim pela mini investigação.

<CodeBlock title="print_estrategico.py" code={`def calcular_total(preco, quantidade):
    total = preco * quantidade
    print(f"preco={preco}, quantidade={quantidade}, total={total}")
    return total

print(calcular_total(12, 3))`} />

Saída:

```text
preco=12, quantidade=3, total=36
36
```

O `print` é simples, mas estratégico. Ele revela o estado interno da função em um ponto específico, e isso ajuda a responder perguntas como: “o valor ficou diferente do esperado?” ou “a entrada chegou como eu imagino?”

## Traceback como leitura de contexto

Um traceback mostra a sequência de falha que ocorreu. Normalmente ele informa:

- módulo e arquivo onde o erro aconteceu;
- linha do código;
- tipo da exceção;
- mensagem útil.

A leitura correta é ler de cima para baixo, identificando a linha exata e depois mirando na causa lógica.

<CodeBlock title="traceback_divisao.py" code={`def dividir(a, b):
    return a / b

print(dividir(10, 0))`} />

Saída real:

```text
Traceback (most recent call last):
  File "/tmp/traceback_divisao.py", line 4, in <module>
    print(dividir(10, 0))
  File "/tmp/traceback_divisao.py", line 2, in dividir
    return a / b
ZeroDivisionError: division by zero
```

Esse exemplo mostra que a exceção foi levantada no `return a / b`, mas a chamada foi feita em `print(dividir(10, 0))`. Em outras palavras, a falha não aparece “do nada”: ela tem origem de código e contexto.

## `breakpoint()` e o debugger

Em Python, `breakpoint()` é um atalho para entrar em um estado de pausa justamente no ponto em que você precisa inspecionar as variáveis. O comando é simples, mas tem um efeito importante: ele transforma um erro em uma investigação ativa.

<CodeBlock title="estado_depuracao.py" code={`def encontra_maior(valores):
    maior = valores[0]
    for valor in valores[1:]:
        if valor > maior:
            maior = valor
        print(f"maior atual: {maior}, valor analisado: {valor}")
    return maior

print(encontra_maior([3, 9, 1, 7]))`} />

Esse exemplo mostra como acompanhar o estado da variável `maior` em cada iteração. Em ambiente de desenvolvimento, você pode usar `breakpoint()` para pausar a execução e observar `valor`, `maior` e o restante da lista no momento exato da decisão.

O VS Code também oferece um debugger visual, muito útil para seguir a execução passo a passo sem poluir o código com `print` em excesso. Em projeto real, a combinação certa é: `print` para inspeções rápidas, debugger para investigação mais profunda e código limpo depois da correção.

<CodeBlock language="bash" title="terminal" code={`python -m pdb app.py`} />

A linha acima é um comando de terminal ilustrativo: o `pdb` é o depurador interativo do Python e ajuda a seguir a execução linha por linha.

## Método científico de depuração

A depuração mais eficiente costuma seguir este fluxo:

1. reproduzir o problema com o menor caso possível;
2. formular uma hipótese sobre a causa;
3. testar a hipótese com uma inspeção ou mudança mínima;
4. confirmar se o problema desapareceu;
5. refatorar o trecho para manter o código legível.

Isso evita o “chute” e cria um loop de correção mais seguro.

<StepThrough>
  <div>
    <p><strong>Etapa 1:</strong> o programa recebe uma lista e tenta achar o maior valor.</p>
  </div>
  <div>
    <p><strong>Etapa 2:</strong> você observa que a variável `maior` começa em `valores[0]` e pode estar errada se a lista vier vazia.</p>
  </div>
  <div>
    <p><strong>Etapa 3:</strong> a correção é validar a entrada antes de usar o índice 0 e, depois, testar com caso vazio e caso normal.</p>
  </div>
</StepThrough>

<CodeBlock title="depuracao_minima.py" code={`def maior_numero(valores):
    if not valores:
        raise ValueError("lista vazia")
    maior = valores[0]
    for valor in valores[1:]:
        if valor > maior:
            maior = valor
    return maior

print(maior_numero([3, 9, 1, 7]))
print(maior_numero([]))`} />

Saída real:

```text
9
Traceback (most recent call last):
  File "/tmp/depuracao_minima.py", line 9, in <module>
    print(maior_numero([]))
  File "/tmp/depuracao_minima.py", line 3, in maior_numero
    raise ValueError("lista vazia")
ValueError: lista vazia
```

Isso mostra uma boa regra: quando você encontra um erro, não corrige adivinhando — você investiga o estado, valida a hipótese e confirma a correção.

## No mercado de trabalho

Em times reais, bugs aparecem em produção, em integrações, em regras de negócio e em rotinas em lote. A pessoa que sabe depurar rapidamente tem um valor enorme porque reduz tempo de parada, evita retrabalho e melhora a confiança em entregas. Isso costuma separar quem apenas “codifica” de quem consegue manter sistemas em funcionamento.

Em ferramentas de negócio, automações, APIs e processamento de dados, a capacidade de investigar o problema sem improvisar costuma ser mais importante do que a velocidade de digitação.
