# Ambientes e projetos

Você já deve ter percebido que, em programação, o ambiente do projeto importa tanto quanto o código. O mesmo programa pode funcionar em um computador e falhar em outro se a versão do Python ou a lista de bibliotecas forem diferentes. Quando você cria um projeto em Python, a prática mais segura é isolar suas dependências em um ambiente virtual: um espaço separado para instalar e usar bibliotecas do projeto sem mexer no sistema global.

Esse conceito é crucial porque a maioria dos erros reais de “funciona na minha máquina” não nasce do algoritmo em si. Ela nasce do ambiente. Talvez a máquina tenha outra versão do Python, outra biblioteca ou outra combinação de pacotes. Ao isolar o ambiente, você reduz esse tipo de problema e deixa o projeto mais previsível e fácil de reproduzir.

## 1. Por que não instalar tudo no sistema?

Imagine que você trabalha em dois projetos diferentes. Um usa uma versão antiga de uma biblioteca e o outro precisa da versão nova. Se você instalar tudo globalmente, os dois projetos competem pelo mesmo estado do ambiente. Isso cria um efeito de “trava” em que o sistema inteiro fica mais difícil de controlar.

O ambiente virtual resolve esse problema criando um espaço isolado para cada projeto. Em vez de compartilhar a mesma instalação global, cada projeto tem sua própria cópia do Python e suas dependências. Isso facilita a reprodução em outros ambientes, a execução em máquinas diferentes e a manutenção do código mais tarde.

<CodeBlock title="estrutura_do_projeto.py" code={`from pathlib import Path

raiz = Path("meu_projeto")
for item in ["app", "src", "tests", ".venv", "requirements.txt"]:
    caminho = raiz / item
    print(item, "->", caminho.exists())`} />

Saída esperada:

```text
app -> False
src -> False
tests -> False
.venv -> False
requirements.txt -> False
```

Esse código apenas simula a estrutura de um projeto em Python e mostra como os diretórios e arquivos aparecem na visão do programa. Em um projeto real, você cria essa estrutura antes de começar a chamar `pip` e instalar dependências. A organização deixa claro o que faz parte do código, o que faz parte do ambiente e o que é dependência externa.

## 2. Venv, ativação e isolamento real

O módulo que cria ambientes virtuais em Python é `venv`. A ideia é simples: você cria uma pasta para o ambiente, por exemplo `.venv`, e aí o Python do ambiente passa a ser usado para esse projeto. Em termos práticos, isso evita mistura entre bibliotecas do sistema e bibliotecas do seu código.

Você normalmente cria o ambiente com `python -m venv .venv`. Depois, ativa o ambiente conforme o sistema operacional. Em Linux ou macOS, costuma ser `source .venv/bin/activate`; em Windows, geralmente é `.venv\Scripts\activate` em PowerShell. O detalhe importante é que a ativação muda o `PATH` do terminal para usar o Python local do projeto.

<CodeBlock title="ambiente_python.py" code={`import os
import sys

print("Python:", sys.executable)
print("Ambiente virtual:", "VIRTUAL_ENV" in os.environ)
print("Versão:", sys.version.split()[0])`} />

Saída esperada:

```text
Python: /usr/local/bin/python
Ambiente virtual: False
Versão: 3.11.x
```

A saída depende do computador em que o código foi executado. O ponto importante é entender que o programa usa o Python do ambiente ativo. Quando `VIRTUAL_ENV` está presente, indica que o interpretador foi trocado para um ambiente virtual. Isso é uma marca de que o projeto está correndo em um contexto isolado e previsível.

## 3. `pip`, `pip list`, `pip freeze` e `requirements.txt`

Quando você instala uma biblioteca externa, a ferramenta usada normalmente é `pip`. Ela lê o pacote adequado para o ambiente atual e faz a instalação. Em seguida, você frequentemente usa `pip list` para ver tudo que está instalado no ambiente e `pip freeze` para gerar uma lista com versões específicas.

Esse arquivo gerado é o `requirements.txt`. Ele é muito útil porque permite reproduzir o ambiente em outra máquina. Em vez de dizer “instale as bibliotecas X, Y e Z”, você usa um único arquivo com as versões exatas e executa a instalação em outro ambiente com o mesmo comando.

A prática correta é: o ambiente do projeto fica isolado; as dependências ficam explícitas; a instalação usa `pip`; e a reprodução usa `requirements.txt`. Isso cria uma cadeia de confiabilidade para o projeto inteiro.

<StepThrough>

## 4. Estrutura de projeto: o que vai em cada pasta?

Um projeto bem organizado não é só “uma pasta com scripts”. Ele costuma ter divisão clara entre código principal, testes, configurações e dependências. Isso não é frescura; é uma forma de reduzir a confusão. Quando você abre um projeto pela primeira vez e consegue localizar rapidamente a lógica principal, os testes e o ambiente, a produtividade cresce muito.

Uma estrutura típica é:

- `app/` ou `src/`: código da aplicação
- `tests/`: testes automatizados
- `requirements.txt`: dependências do projeto
- `.venv/`: ambiente virtual
- `README.md`: instruções de uso

<CodeBlock title="listar_pastas.py" code={`from pathlib import Path

for item in ["src", "tests", ".venv", "requirements.txt", "README.md"]:
    caminho = Path(item)
    print(f"{item}: {'sim' if caminho.exists() else 'não'}")`} />

Saída esperada:

```text
src: sim
tests: sim
.venv: sim
requirements.txt: sim
README.md: sim
```

O ponto aqui é a clareza da convenção. O ambiente virtual não deve ser tratado como “uma pasta qualquer”. Ele é uma parte da configuração do projeto e precisa ser reconhecido como tal. A mesma ideia vale para requisitos e estrutura de diretórios: você quer que o processo seja repetível e compreensível para outra pessoa ou para você, meses depois.

## No mercado de trabalho

Em qualquer time de software, o ambiente do projeto não é um detalhe de “configuração”. Ele define se o projeto roda, se ele se comporta como esperado e se alguém consegue reproduzir seu código em uma máquina nova. Desenvolvedores e analistas de dados, automação, backend e dados trabalham com ambientes virtuais como rotina.

Quando você entende isso, passa a confiar mais no fluxo de trabalho profissional: separar ambiente, registrar dependências, manter versões e documentar como reinstalar tudo. Isso reduz retrabalho e melhora a colaboração. Em empresas, a pessoa que consegue “reproduzir o ambiente” costuma ser vista como alguém que resolve a parte mais dolorosa da análise e do desenvolvimento.
