# Encapsulamento e propriedades

Quando você cria uma classe, você precisa decidir quais dados podem ser alterados diretamente e quais devem passar por regras. O encapsulamento é exatamente isso: você protege o estado interno do objeto e oferece uma interface clara para leitura e escrita.

O conceito é simples, mas muito poderoso. Em vez de deixar qualquer parte do programa mexer no saldo de uma conta diretamente, você cria um caminho controlado e validado. Isso reduz bugs e deixa o código mais previsível.

<Callout type="importante" title="O que você vai aprender">
  - Como usar convenção de atributos privados com `_`.
  - Como `@property` expõe leitura controlada.
  - Como `@valor.setter` valida entradas antes de mudar o estado.
  - Como esse padrão reduz erros em classes reais.
</Callout>

## Atributos privados e convenção de uso

Em Python, “privado” não é uma barreira rígida como em algumas outras linguagens. O que existe é uma convenção: atributos internos geralmente começam com underscore, como `_saldo` ou `_email`. Isso informa ao restante do código que aquilo não deve ser alterado diretamente sem cuidado.

A ideia é simples: o objeto guarda suas informações internas e usa métodos ou propriedades para oferecer acesso seguro.

<CodeBlock title="conta_privada.py" code={`class Conta:
    def __init__(self, titular, saldo_inicial=0):
        self.titular = titular
        self._saldo = saldo_inicial

    def depositar(self, valor):
        if valor <= 0:
            raise ValueError("Valor deve ser positivo")
        self._saldo += valor

conta = Conta("Maria", 100)
conta.depositar(50)
print(conta.titular)
print(conta._saldo)
`} />

Saída:

```text
Maria
150
```

Esse padrão é útil porque o código externo ainda consegue usar a conta, mas a regra de negócio fica dentro da classe. Em vez de alterar `_saldo` em qualquer lugar, a conta decide como aceita ou rejeita mudanças.

## Propriedades com `@property`

A propriedade é uma forma elegante de expor um valor como se fosse um atributo normal, mas com lógica por trás. Você usa `@property` para criar um getter. Com isso, `conta.saldo` parece ser um atributo comum, mas a classe pode decidir como calcular ou validar o valor retornado.

<CodeBlock title="conta_property.py" code={`class Conta:
    def __init__(self, titular, saldo_inicial=0):
        self.titular = titular
        self._saldo = saldo_inicial

    @property
    def saldo(self):
        return self._saldo

    @saldo.setter
    def saldo(self, valor):
        if valor < 0:
            raise ValueError("Saldo não pode ser negativo")
        self._saldo = valor

conta = Conta("Ana", 80)
print(conta.saldo)
conta.saldo = 120
print(conta.saldo)
`} />

Saída:

```text
80
120
```

Note que o código fora da classe usa `conta.saldo`, mas quem aplica a regra é o setter. Isso deixa a API da classe mais limpa e segura. Se a regra mudar um dia, você mexe em um só lugar.

A diferença fica clara: em um caso, qualquer parte do programa pode escrever qualquer valor. No outro, a classe decide se o valor é válido.

## Validação em setters

A validação é um dos usos mais valiosos de `@property`. Em vez de aceitar qualquer entrada, a classe especifica quais regras são verdadeiras para o seu domínio.

<CodeBlock title="pessoa_validacao.py" code={`class Pessoa:
    def __init__(self, nome, idade):
        self._nome = nome
        self._idade = idade

    @property
    def idade(self):
        return self._idade

    @idade.setter
    def idade(self, valor):
        if not isinstance(valor, int):
            raise TypeError("Idade deve ser um inteiro")
        if valor < 0:
            raise ValueError("Idade não pode ser negativa")
        self._idade = valor

p = Pessoa("João", 30)
p.idade = 31
print(p.idade)
`} />

Saída:

```text
31
```

Esse padrão deixa o código mais robusto, porque erros de regra de negócio aparecem logo na atribuição, perto da origem do problema.

## Por que isso importa?

Em sistemas maiores, vocês vão notar que muitas falhas acontecem quando o estado interno é alterado sem controle. Um valor que deveria ser positivo vira negativo; um e-mail sem arroba passa a ser aceito; uma idade inteira vira string. O encapsulamento ajuda a impedir esse tipo de quebra antes que ela se espalhe pelo programa.

<Callout type="erro-comum" title="Setter sem validação">
  ```python
  class Conta:
      def __init__(self, saldo=0):
          self._saldo = saldo

      @property
      def saldo(self):
          return self._saldo

      @saldo.setter
      def saldo(self, valor):
          self._saldo = valor

  conta = Conta(50)
  conta.saldo = -100
  print(conta.saldo)
  ```

  Saída real:

  ```text
  -100
  ```

  A classe aceita saldo negativo porque o setter não validou a regra. A correção é verificar `if valor < 0` e lançar um erro, como `ValueError`.
</Callout>

<Callout type="erro-comum" title="Usar `_saldo` em qualquer lugar do programa">
  ```python
  class Conta:
      def __init__(self, saldo):
          self._saldo = saldo

  conta = Conta(100)
  conta._saldo = -500
  print(conta._saldo)
  ```

  Saída real:

  ```text
  -500
  ```

  Isso funciona, mas vai contra o encapsulamento. O objetivo é limitar o acesso e centralizar as regras em um lugar só, em vez de editar o estado interno sem controle.
</Callout>

No mercado de trabalho

Em sistemas de conta, cadastro, pagamentos e gestão de dados, encapsulamento é quase sempre parte do desenho da solução. Desenvolvedores experientes preferem classes que protegem seus dados e deixam as regras explícitas. Isso reduz retrabalho em manutenção e facilita a revisão por outra pessoa.
