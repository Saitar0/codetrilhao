# Git básico: guardar mudanças sem perder o caminho

Programar sozinho costuma parecer simples até você precisar voltar atrás, comparar versões ou entregar um projeto para outra pessoa. Git é a ferramenta que resolve esse problema: ele registra o histórico do projeto, permite analisar mudanças e ajuda a trabalhar em equipe sem mesclar tudo em um caos.

<Callout type="importante" title="O que você vai aprender">
  - Como iniciar um repositório com `git init`.
  - Como registrar mudanças com `add`, `commit`, `status` e `log`.
  - Como separar trabalho com `branch` e mesclar com `merge`.
  - Como proteger o projeto com `.gitignore` e escrever README melhor.
</Callout>

## Repositório e histórico

Um repositório Git guarda a linha do tempo do seu projeto. Você pode pensar nele como um caderno de versões: cada commit é um ponto salvo, com uma mensagem que explica o que mudou.

No terminal, o fluxo mais comum começa assim:

<CodeBlock language="bash" title="terminal" code={`git init
git status
git add .
git commit -m "feat: inicializa projeto de cálculo"`} />

Esse conjunto de comandos cria o repositório, mostra o estado atual, prepara os arquivos e registra a primeira versão. Em projetos reais, o `git status` é essencial: ele mostra o que foi modificado, o que está em staging e o que ainda precisa ser commitado.

<CodeBlock language="bash" title="terminal" code={`git status
git log --oneline

# exemplo de saída
# On branch main
# nothing to commit, working tree clean
# a1b2c3d feat: inicializa projeto de cálculo`} />

A saída do `git log` ajuda a entender o que foi entregue e em que sequência. Isso é muito útil quando você quebra algo e precisa voltar a um ponto anterior.

## Commits pequenos e descritivos

O hábito mais importante de Git não é “fazer um commit por tudo”. É “fazer commits pequenos e claros”. Um commit gigante com mensagem genérica como “ajustes” deixa o histórico confuso e reduz a capacidade de analisar o que mudou.

Uma boa mensagem explica a intenção. Exemplo:

```text
feat: valida entrada de CPF
fix: corrige cálculo de desconto
docs: adiciona guia de uso no README
```

<Callout type="erro-comum" title="Commit gigante 'ajustes'">
  ```bash
git add .
git commit -m "ajustes"
  ```

  O problema não é o comando em si; é o contexto. Esse tipo de mensagem não diz o que foi alterado, nem por quê. A correção é separar por intenção: um commit para correção, outro para documentação, outro para testes.
</Callout>

Quando o histórico está bem organizado, a revisão do código fica muito mais fácil. Isso vai além da disciplina: é uma habilidade de comunicação com o time e com você mesmo no futuro.

## Branches e merge

Branches permitem trabalhar em paralelo sem mexer diretamente na linha principal do projeto. É como abrir outra trilha de trabalho em um rio: você pode experimentar uma ideia e, depois, decidir se ela entra no fluxo principal.

<CodeBlock language="bash" title="terminal" code={`git checkout -b feature/validacao-cpf
git status
git commit -m "feat: adiciona validação de CPF"
git checkout main
git merge feature/validacao-cpf`} />

A ideia principal é simples: você cria uma branch para uma alteração, valida o trecho, e depois integra com `merge`. Isso evita que uma alteração incompleta ou experimental afete o código principal antes do momento certo.

<CodeBlock language="bash" title="terminal" code={`git branch
git branch --merged`} />

Se você olhar o histórico de um projeto profissional, verá que branches são muito usadas para novas features, correções urgentes e experimentos. Mesmo em projetos pequenos, esse fluxo ajuda a manter a organização.

## `.gitignore` e proteção de dados sensíveis

Um erro muito comum é subir arquivos locais como `.venv`, cache de IDE, `.env`, senhas, logs e bancos de dados para o GitHub. Isso pode expor dados sensíveis e também gerar commit ruim.

O `.gitignore` serve justamente para dizer ao Git: “este arquivo não entra no histórico”.

```gitignore
# .gitignore
.venv/
__pycache__/
.env
secrets.json
*.log
```

<Callout type="erro-comum" title="Subir .venv e senhas ao Git">
  ```gitignore
  .venv/
  .env
  secrets.txt
  ```

  Se esses arquivos forem commitados, você pode expor configurações internas e dados sensíveis. A correção é configurar `.gitignore` antes do primeiro commit relevante e revisar o estado do repositório com `git status`.
</Callout>

Esse cuidado é essencial em projetos pessoais e profissionais. Uma vez que um segredo entra no histórico, ele pode ser difícil de remover totalmente sem atenção e planejamento.

## README e GitHub

Quando você escreve um projeto, o README funciona como porta de entrada. Ele explica para alguém novo como instalar, executar e usar o código. Isso é especialmente importante em projetos compartilhados ou em portfólio.

Um README comum inclui:

- descrição do projeto;
- instruções de instalação;
- passos de execução;
- exemplos de uso;
- links para documentação ou testes.

<CodeBlock language="bash" title="terminal" code={`git remote add origin https://github.com/seu-usuario/seu-projeto.git
git push -u origin main

# depois:
git pull origin main`} />

O GitHub transforma o repositório em um ambiente colaborativo. Você pode enviar alterações, acompanhar a evolução do projeto e receber revisão de código ou sugestões. Isso também é parte do portfólio de um desenvolvedor.

<CodeTabs>
  <div label="Fluxo básico">
    <CodeBlock language="bash" code={`git status
git add .
git commit -m "feat: adiciona lógica inicial"
git push origin main`} />
  </div>
  <div label="Fluxo com branch">
    <CodeBlock language="bash" code={`git checkout -b feature/ajustes
git add .
git commit -m "fix: corrige regra de validação"
git checkout main
git merge feature/ajustes`} />
  </div>
  <div label="Fluxo para revisão">
    <CodeBlock language="bash" code={`git pull origin main
git checkout -b review/README
git add README.md
git commit -m "docs: melhora instruções de uso"`} />
  </div>
</CodeTabs>

## No mercado de trabalho

Git e GitHub são quase um requisito em projetos de software. Eles permitem que times trabalhem em paralelo, revisem mudanças e mantenham um histórico claro. Em processos reais, isso influencia produtividade, confiabilidade e comunicação. Quem domina Git consegue colaborar sem perder trabalho, entender o que foi alterado e entregar código em ambiente profissional.

Além disso, um histórico limpo aumenta a credibilidade em portfólios, entrevistas e projetos colaborativos. O Git deixa evidente o seu pensamento em código e a disciplina de entrega.
