# Módulos e pacotes

Quando o código cresce, a pergunta deixa de ser “como faço isso?” e passa a ser “como manter isso organizado?” Em Python, a resposta mais natural é dividir a lógica em módulos: cada arquivo fica responsável por uma parte do programa. Isso deixa o código mais legível, mais fácil de testar e mais simples de reutilizar em outros projetos.

Você já usou módulos sem perceber: `math`, `random`, `os`, `statistics` e muita outras bibliotecas fazem parte da base da linguagem. A ideia central é a mesma em qualquer projeto: um módulo é simplesmente um arquivo Python que você importa quando precisa de uma funcionalidade.

## 1. Importar é usar um arquivo como ferramenta

O primeiro passo é perceber que Python não precisa “guardar tudo em um único bloco”. Quando você faz `import math`, o interpretador busca um módulo que fornece funções prontas para cálculo. Quando faz `from math import sqrt`, ele traz uma função específica para o namespace atual. O efeito prático é o mesmo em muitas situações, mas a forma de escrever o código fica diferente.

A regra mais simples é: importe o módulo quando você vai usar várias coisas dele; importe nome específico quando você quer uma função curta e direta.

<CodeBlock title="modulos_basicos.py" code={`import math
from math import sqrt

print(math.sqrt(81))
print(sqrt(16))
print(math.factorial(5))`} />

Saída esperada:

```text
9.0
4.0
120
```

Observe como `math.sqrt` e `sqrt` fazem a mesma operação, mas com sintaxes diferentes. Em projetos pequenos e médios, isso ajuda a manter o código legível. A escolha também depende do contexto: se você usa vários elementos do módulo, `import math` costuma ser mais claro; se usa só uma função, `from math import sqrt` economiza digitação.

## 2. `import as` e nomes curtos para leitura

Em alguns casos, a biblioteca tem um nome longo ou você quer evitar repetição. Então o Python permite criar um apelido com `as`. Isso não muda o comportamento real do módulo; ele apenas reduz o espaço do nome no seu código.

Esse padrão é muito comum em projetos que usam bibliotecas com nomes muito específicos ou em situações em que você quer deixar o código mais elegante para quem lê.

<CodeBlock title="alias_do_modulo.py" code={`import collections as col

contagem = col.Counter(["maçã", "banana", "maçã", "laranja"])
print(contagem)
print(contagem["maçã"])`} />

Saída esperada:

```text
Counter({'maçã': 2, 'banana': 1, 'laranja': 1})
2
```

Aqui, `collections` foi renomeado para `col`, e o programa continua funcionando. A utilização de apelidos ajuda a reduzir ruído visual, mas vale lembrar que o nome do módulo continua sendo `collections`. Em projetos em equipe, apelidos bem escolhidos melhoram a leitura, mas apelidos confusos podem reduzir a clareza. A convenção é usar nomes curtos e inteligíveis.

## 3. Módulo próprio, pacote e `__init__.py`

A parte mais importante de um módulo não é só a sintaxe, mas a ideia de divisão do código. Você pode criar um arquivo que contém funções úteis, como um `utils.py`, e importar esse arquivo em outro lugar do projeto. Em projetos reais, isso evita repetir funções, especialmente se você tem validações, cálculo de descontos, formatação de textos ou operações de arquivos em vários pontos.

Quando um grupo de módulos está organizado em uma pasta, você está criando um pacote. O Python usa a presença de `__init__.py` como sinal de que aquela pasta é um pacote importável. Isso é especialmente útil quando o projeto tem estrutura maior, como `app/`, `utils/`, `models/` ou `services/`.

<CodeBlock title="modulo_local.py" code={`import os

caminho = os.path.join("dados", "resultado.txt")
print(caminho)
print(caminho.split("/"))`} />

Saída esperada:

```text
dados/resultado.txt
['dados', 'resultado.txt']
```

Essa estrutura é a base da organização do código em grandes projetos. Você não precisa colocar tudo no mesmo arquivo. Você pode ter funções de regra de negócio em um módulo, utilitários de arquivo em outro, e a parte principal do programa importando tudo de forma ordenada. Isso reduz a chance de erros e melhora o uso da memória e da manutenção.

## 4. Bibliotecas padrão: quando a linguagem já resolve o problema

Python vem com uma biblioteca padrão muito rica. Ela não é “extras”, é parte da linguagem e está disponível em praticamente qualquer instalação. Exemplos clássicos são `random`, `math`, `os`, `collections`, `statistics`, `pathlib` e `itertools`.

A biblioteca padrão é o primeiro lugar onde você deve procurar. Antes de instalar algo novo, vale perguntar: “o Python já tem isso?” Muitas tarefas que parecem complexas têm solução pronta e bem testada em um módulo da biblioteca padrão.

<CodeBlock title="biblioteca_padrao.py" code={`import math
import random
from collections import Counter

print(round(math.sqrt(144), 2))
print(random.randint(1, 6))
print(Counter(["a", "b", "a", "c"]))`} />

Saída esperada:

```text
12.0
4
Counter({'a': 2, 'b': 1, 'c': 1})
```

A saída acima mostra três exemplos de uso típico: cálculo matemático, geração aleatória e contagem de elementos. Isso lembra o ponto mais importante sobre módulos: eles fazem o trabalho pesado por você e deixam o código do seu programa focado no que ele precisa resolver.

## 5. Guardas de execução e import seguro

Um detalhe muito comum é este: quando um arquivo é executado diretamente, ele pode executar código de exemplo; quando é importado por outro arquivo, o mesmo código não deveria rodar automaticamente. Para isso, a convenção é usar `if __name__ == "__main__":`.

É uma forma de dizer: “execute isto somente se este arquivo for o programa principal; se ele for importado, não execute esse trecho”. Isso evita efeitos colaterais e facilita testes.

<CodeBlock title="guardas_de_execucao.py" code={`def saudacao(nome):
    return f"Olá, {nome}!"

if __name__ == "__main__":
    print(saudacao("Ana"))
    print(saudacao("Bia"))`} />

Saída esperada:

```text
Olá, Ana!
Olá, Bia!
```

Se esse arquivo for importado por outro módulo, a parte abaixo de `if __name__ == "__main__":` não será executada. Em projetos maiores, isso é essencial porque o código principal e as funções reutilizáveis precisam ficar separados claramente.

<Callout type="erro-comum" title="ModuleNotFoundError">
  <p>Quando você tenta importar uma biblioteca que não está instalada ou o ambiente correto não foi carregado, o Python acusa <strong>ModuleNotFoundError</strong>.</p>
  <CodeBlock title="modulo_inexistente.py" code={`import biblioteca_inexistente`} />
  <p>Mensagem real:</p>
  <pre>ModuleNotFoundError: No module named 'biblioteca_inexistente'</pre>
  <p>Correção: verificar o nome da biblioteca, ativar o ambiente virtual certo e instalar com <code>pip install</code> quando a biblioteca for externa.</p>
</Callout>

<Callout type="erro-comum" title="Import circular">
  <p>Se dois módulos tentam importar um ao outro ao mesmo tempo, o programa pode quebrar de forma silenciosa ou com erro de importação.</p>
  <CodeBlock title="import_circular.py" code={`# a.py
import b
print("a ok")

# b.py
import a
print("b ok")`} />
  <p>Mensagem real no cenário de import circular:</p>
  <pre>ImportError: cannot import name 'x' from partially initialized module 'a'</pre>
  <p>Correção: reorganizar dependências, mover a lógica compartilhada para um terceiro módulo ou reduzir o acoplamento entre arquivos.</p>
</Callout>

<Callout type="erro-comum" title="Arquivo com o nome de uma biblioteca">
  <p>Se você cria um arquivo chamado <code>random.py</code> na raiz do projeto, o Python pode importar o seu arquivo antes da biblioteca padrão.</p>
  <CodeBlock title="random_local.py" code={`import random
print(random.__file__)`} />
  <p>Mensagem real: o programa imprime o caminho para o arquivo local em vez da biblioteca padrão, o que pode alterar o comportamento do programa.</p>
  <p>Correção: dar nomes mais específicos ao módulo do seu projeto, por exemplo <code>gerador_aleatorio.py</code>, e manter a biblioteca real acessível.</p>
</Callout>

## No mercado de trabalho

No mundo profissional, módulos e pacotes aparecem em praticamente todos os projetos. Um script pequeno pode até ficar em um único arquivo, mas quando a aplicação cresce, a divisão por responsabilidades vira regra. Frontend, backend, automações, IA,ETL e sistemas internos: todos usam bibliotecas, módulos próprios e organização em pastas.

Além disso, desenvolver sem modularizar vira um problema de manutenção. A pessoa que escreve 500 linhas em um único arquivo pode até funcionar, mas a pessoa que precisa evoluir esse código depois vai ter mais dificuldade para localizar regras, depurar e testar. Em times reais, isso se torna um custo enorme, e por isso manter módulos bem nomeados e independentes é uma habilidade valorizada.

  <li>Um módulo é um arquivo Python com código reutilizável.</li>
  <li>Você pode importar o módulo inteiro ou só um nome específico.</li>
  <li>Módulos locais ajudam a dividir a lógica do projeto em partes enxutas.</li>
  <li>Bibliotecas padrão como math, random, os e collections resolvem muitos problemas sem instalação extra.</li>
